# Daily private audio publishing

The approved connection is an owner-private hosted relay to a PIN-protected listener.
It keeps publishing authorization server-side. A fresh cloud runtime obtained native
service access and replayed a completed test successfully without laptop credentials
on 18 October 2026. This verifies the connection, not the entire scheduled news,
narration and delivery workflow.

Origins, Site identifiers, credentials, actual episode IDs, private transcripts and
receipts belong in the approved private runtime/ledger, never this public repository.
The existing upstream Claude/Gmail workflow is unchanged.

## Daily sequence

1. Load current instructions, feedback and the private delivery/event ledger. Record
   the source revision and a bounded intake cutoff. Start at 07:00 Asia/Singapore;
   07:30 is a delivery target, not a guaranteed SLA.
2. Research, verify and deduplicate the report; render the approved narration.
   Measure actual MP3 duration, decode the full file, check clipping/loudness and
   chapter positions, and compute its byte size and SHA-256.
3. Obtain fresh supported native service access for the existing owner-private Site.
   Do not use local Cloudflare OAuth, the deployment token or the listening PIN.
   Native service access is not a signed-in visitor identity; preserve the Site's
   owner-only dispatch boundary.
4. Call the non-publishing credential check. Then send the approved MP3 through
   the relay and persist the exact request metadata plus returned receipt privately.
5. Verify edition, size, SHA-256 and seven-day expiry. A completed exact replay can
   verify the durable receipt without another episode. Playback readback is a
   separate authenticated listener check. Only then mark the corresponding delivery
   stage complete; record unavailable checks honestly.

## Non-publishing preflight

`POST /api/operations/relay/check` on the configured private Site:

- Native service authorization: `OAI-Sites-Authorization: Bearer <native service access>`.
- `Origin`: the exact Site origin.
- `X-Brief-Relay: 1`.
- Empty request body.

The server sends an empty, deliberately invalid MIME request to its fixed listener.
The listener checks publishing authorization before rejecting that MIME type, so
only the exact expected rejection establishes authentication. No audio, episode or
receipt is created. The Site returns sanitized results, never the upstream body:

| Result | Meaning |
|---|---|
| 200, `authenticated:true, probeOnly:true` | Credential match |
| 401 | Native access denied, or publishing credential rejected; inspect the sanitized code |
| 403 | Origin/custom-header checks failed |
| 503 | Missing server setup or unavailable downstream configuration |
| 502 | Network failure or an unexpected downstream result |

Secret/config changes take effect after a saved Site version is deployed. A
successful check does not activate forwarding or certify the daily render.

## Real MP3 upload

`POST /api/operations/relay` on the same private Site. Use raw MP3 bytes, not
multipart, JSON or a private download URL. Never put credentials in a query string.

| Header | Contract |
|---|---|
| `OAI-Sites-Authorization` | Fresh native Site service access, as above |
| `Origin` | Exact Site origin |
| `X-Brief-Relay` | Exact value `1` |
| `Content-Type` | Exact value `audio/mpeg` |
| `Content-Length` | Exact byte count; 8 through 8,388,608 bytes (8 MiB) |
| `X-Brief-Edition` | Required real calendar date `YYYY-MM-DD`; use the intended Singapore edition |
| `X-Episode-Title` | Optional editorial title, at most 120 characters and no control characters; defaults to edition |
| `X-Episode-Chapters` | Optional JSON array, at most 30 `{title,start}` objects; defaults to `[]` |

Each chapter title is at most 80 characters; `start` is a finite, nonnegative
number of seconds from the beginning. Check starts against measured duration.
Use ASCII-safe HTTP header values; JSON chapter labels can use Unicode escapes.
Do not append voice, build or duration diagnostics to the editorial title.

**There is no duration header.** The player measures duration from audio; keep
rendered duration in the private operational ledger. Upload time is generated by
the listener in UTC epoch seconds, independently of the supplied edition date.
The downstream sorts chapter positions. Retrying must preserve the original bytes,
title and chapter JSON structure/order; changed metadata is a conflict.

The relay enforces MP3 frame sanity and bounded reads, not full decoding or content
quality. Its upstream request has a 20-second timeout, a fixed HTTPS target and no
redirect following. It never forwards caller cookies, caller authorization or a
request-supplied destination. Reduce bitrate if the complete episode exceeds 8 MiB;
do not truncate it or silently opt into paid infrastructure.

## Receipt, readback and retry behavior

A new confirmed upload returns HTTP 201:

```json
{
  "receipt": {
    "id": "<episode UUID>",
    "created": 0,
    "expires": 604800,
    "size": 0,
    "edition": "YYYY-MM-DD",
    "sha256": "<audio SHA-256>"
  },
  "reused": false
}
```

The numbers above illustrate types only. Actual `created`/`expires` are UTC epoch
seconds, `expires-created` must be 604800, and `size` must equal the uploaded bytes.
The relay computes the audio hash and checks the downstream receipt before saving it.

There is **no separate GET receipt route**. Resend an exact completed request to
receive HTTP 200 with the same receipt and `reused:true`, without another upload.
The durable key is edition plus audio hash; the editorial fingerprint also covers
title and chapters. This protects transport retries, not semantic news dedup across
editions. Use the private event/delivery ledger for that editorial work.

| Result | Action |
|---|---|
| 201 | Persist and verify the new receipt |
| 200 + `reused:true` | Existing completed delivery; verify same ID/hash/expiry |
| 400 / 413 / 415 | Correct invalid metadata, size or MP3 before a new attempt |
| 401 / 403 / 503 | Stop and diagnose access or configuration; do not widen permissions |
| 409 | Conflict, in-flight or uncertain prior send: reconcile existing state |
| 502 / client timeout | Delivery may be uncertain: do not bypass the reservation or upload directly |

An interrupted request may leave a `sending` reservation. Ambiguous upstream sends
become `uncertain`. Neither state is automatically resent: the listener itself
creates a fresh UUID on every direct upload. An operator must reconcile downstream
metadata/audio and the receipt state before recovery. Never delete a reservation
just to force another send.

Listener `GET /api/episodes/{id}` returns private metadata and
`GET|HEAD /api/media/{id}` serves private audio, including supported byte ranges,
only with a valid listening session. The publishing credential grants no read
access. Receipt replay proves durable publication state; independent authenticated
audio hashing/playback remains a separate verification step.

## Retention, defaults and remaining limits

New Cloudflare audio and the disposable active-list index have native seven-day
storage expiry. Private metadata is retained; authenticated reads enforce expiry.
Downloaded copies cannot be revoked. The original owner-private fallback's storage
cleanup is not established by Cloudflare expiry configuration.

The listener selects the newest active recording by upload time. A later connection
test can displace the day's real recording. Keep test fixtures labelled and out of
the normal active listing once verification is complete. A reversible operator
action can preserve a private restore copy, then exclude only the disposable test
index entry; retain the audio and metadata, and never rewrite publication time to
make a test look older. There is currently no public test-exclusion API.

The connection test was small. It does not certify a production-sized relay
transfer, physical-device playback, elapsed seven-day production expiry or the first
complete scheduled run. Free quotas, CPU/memory, platform availability, source access
and synthesis availability remain limits. The repo contains no autonomous research
or speech engine, and editing these instructions does not reconfigure a scheduler.
